# B2B Platform — Slice 2: Wallet and Razorpay top-up — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every agency has an INR prepaid balance it tops up by bank transfer (admin-approved) or Razorpay (webhook-credited), sees as a two-sided statement, and that platform admins can adjust, mark as test, and close; holds, debits, credits and receivables exist as a service API that slice 3's booking flow calls.

**Architecture:** Public-schema tables (`wallet`, `wallet_entry`, `topup_request`, `gateway_order`, `gateway_webhook_orphan`, `platform_receivable`). All balance arithmetic lives in a pure `WalletMath` (property-tested); `WalletService` is the only writer, every mutating method `@Transactional(propagation = REQUIRES_NEW)` and locks the wallet row with `findByTenantIdForUpdate` before posting. Entries are append-only; `available = balance − held`; HOLD/HOLD_RELEASE move `held` only. Payment gateway is an interface with `RazorpayPaymentGateway` (REST + HMAC, no SDK) and `StubPaymentGateway` (default until the owner sends keys) selected by `app.payments.provider`.

**Tech Stack:** Spring Boot 3.3 / Java 17 / Flyway / `RestClient` / Mockito + `@WebMvcTest`; Next.js 15 / React 19 / `components/ui` / Playwright; Razorpay Checkout (`https://checkout.razorpay.com/v1/checkout.js`) loaded only on the top-up modal.

**Deviations (rulings):**
- Wallet writes run `REQUIRES_NEW` but do not clear `TenantContext`: the tenant `search_path` is `tenant_x, public` and no tenant table shares a wallet table's name, so the row lock is the same either way; `REQUIRES_NEW` is what makes the debit commit before any later tenant mirror. Cost if wrong: a tenant table named `wallet` would shadow it — the V18 migration comment records the names (no test pins them yet).
- Emails become a `NotificationService` with a logging implementation (no mail dependency in the repo yet). Low-balance and orphan alerts call it; slice 6 adds SMTP.
- Razorpay keys come from env (`RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`), not a platform credential table. With `app.payments.provider=stub` (default) top-ups get a fake order id and a test-only "Simulate payment" endpoint drives the same webhook handler.
- Agents get no wallet screen in this slice (slice 3's wizard shows the balance); owner manages, accountant reads.

**Branch:** `feat/b2b-platform` in both repos (continue; never push to main).

## Global Constraints

- Everything in the slice 1 plan's Global Constraints (`docs/superpowers/plans/2026-10-23-b2b-01-foundation.md`) still holds: blueprint audit rules, `@Schema` on every DTO field, ids via `UniqueIdResolver`, `TIMESTAMPTZ`/`Instant`, `BigDecimal` + `NUMERIC(19,2)`, no JPA relationships, `SecurityContextUtil` only, controller test setup, `UI_BLUEPRINT.md` for every screen.
- Next public migration is **V18**. Wallet currency is `'INR'` only.
- Wallet never goes negative: `available ≥ 0` and `balance ≥ held ≥ 0` after every posting. A shortfall becomes a `platform_receivable` (DUE) that blocks holds.
- Every mutating wallet call takes an `idempotencyKey`; the same key returns the existing entry and posts nothing.
- Platform admin actions go to `PlatformAuditService.record` with new `PlatformAuditAction` values `WALLET_ADJUST`, `WALLET_CLOSE`, `WALLET_TEST_FLAG`, `TOPUP_DECISION`, `TOPUP_PROOF_VIEW`.

## Review Focus

1. **Razorpay retries the same `payment.captured` webhook (and `order.paid` for the same payment)** — exactly one TOPUP entry; idempotency key is `gw:` + payment id for both events. Test in Task 5.
2. **Admin approves a bank top-up twice (double click / two admins)** — one credit; second call 409. Request row locked `FOR UPDATE`. Test in Task 4.
3. **A credit arrives while a receivable is DUE** — receivable settled first (`RECEIVABLE_SETTLED`), remainder to balance; a credit smaller than the receivable settles it partially and leaves it DUE with the reduced amount. Test in Task 2.
4. **Closing a wallet with an open hold, a DUE receivable or a PENDING top-up** — refused with a message naming the blocker. Test in Task 3.
5. **Bank reference reused (same UTR typed by two agencies or twice)** — refused with a field error on `bankRef`, case- and space-insensitive. Test in Task 4.
