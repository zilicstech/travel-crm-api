01

Design principles

Eight rules the rest of the document obeys. Breaking one is a design change, not a detail.

P1

One screen, one table, zero joins

Every list view answers to a single SELECT with a WHERE and an ORDER BY. No joins, no subselects, no stitching in the app layer.

P2

Denormalize names, never facts

A row snapshots anything it shows but does not own — client_name, agent_name, service_label. Renames bulk-update every snapshot in the same transaction.

P3

Money is recomputed, never trusted

Stored totals exist for query speed only. Every write recomputes them from current lines. A stored value is never an input to a calculation.

P4

One wide table, not one per variant

All four service types live in one table with nullable per-type columns. Four tables or a supertype would cost a join on the most-loaded screen in the product.

P5

JSONB only where the shape repeats

Exactly two JSONB columns exist: flight sectors and per-traveller visa ticks. Everything else is typed. JSONB is an escape hatch, not the default.

P6

Derived data is computed

The trip schedule, the visa roll-up, margins — all computed on read. A column may only be stored if it removes a join from a named list screen.

P7

Nothing a customer could dispute is deleted

Travellers drop with a reason, follow-ups complete with a timestamp, services cancel. Hard deletes exist only for correctable clerical entries.

P8

Every detail field is optional

The agent takes an enquiry on a phone call and knows which services are wanted, rarely more. Completeness is gated at proposal time, never by NOT NULL.

02

Class model

Four new tables, five altered. Relationship map, class-by-class fields, and how each UI field maps to a column.

the lead — every child hangs off it new table always set nullable service_id

Ownership rule. lead_id is on every child row, always. service_id is a refinement, never a replacement — cascade, agent-scoping and tenant queries all travel through lead_id, so a child row is never orphaned by a service being removed. That nullability is load-bearing: an agency fee, a courier charge or an invoice covering flight-plus-hotel together has no single owning service, and forcing one would either invent a fake service or lose the charge.

Why one wide table

ShapeWhat it costs
Four tables, one per typeLead detail needs 4 queries or 4 LEFT JOINs. The cross-lead board becomes a 4-way UNION. A fifth type touches every query.
Supertype + subtype tablesEvery read is a join. Worst of both worlds.
One table, all details in one JSON blobNo index on hotel_check_in or visa_appointment_date, no date typing, reporting becomes string-matching inside JSON.
One wide table, typed columns + 2 JSONBSparse rows — most columns NULL on any row. Postgres stores a NULL as roughly one bit in the row header. One entity, one query, no dispatch.

The sparseness is the price, and it is the cheap side of the trade. A NULL column costs a bit; a join costs a query plan.

The label, and why it is stored

A lead holding two hotels has to call them different things everywhere — the tab strip, the trip details list, the costing table, the timeline entry, and a deep link pasted to a colleague. The rule, ported from the frontend:

  • One service of this type on the lead → the plain type name: Hotel.
  • Otherwise use the type's natural naming field — flight route, hotel city, visa country, transfer pickup → Hotel — Phuket.
  • Two siblings resolving to the same source → append an ordinal: Hotel — Phuket (2).
  • Source field still blank → positional fallback: Hotel 2.

Sync obligation

The label depends on its siblings, and the cross-lead board never loads the sibling set — so it cannot be computed on read there. It is a P2 snapshot: any write that adds, removes or renames a service re-derives and bulk-updates label for every service on that lead, in the same transaction. One extra UPDATE over a set that is realistically under ten rows.

visa_checklists — one set of ticks per application

{"M5":  {"passportCollected": true,  "photosCollected": true,  "formsFilled": false,
         "submittedToEmbassy": false, "approved": false, "passportReturned": false},
 "M12": {"passportCollected": true,  "photosCollected": false, "formsFilled": false,
         "submittedToEmbassy": false, "approved": false, "passportReturned": false}}

Keyed by member_id, never by array index — the traveller list is filtered and sorted in the UI, and an index would silently retarget the ticks onto the wrong person. A trip carrying a Thailand visa and a Japan visa needs two fully independent sets; the old lead-wide checklist made both applications share and overwrite each other.

Known limitation, accepted

passportCollected and passportReturned are physically one fact per traveller per trip — you collect the passport once even if you file two visas with it. The UI already shows a note to that effect when a lead holds more than one visa. Splitting those two keys onto lead_members later is purely additive and does not change this table.

Status and assignment

NOT_STARTED ──accept──▶ IN_PROGRESS ◀──▶ AWAITING_CLIENT ──▶ CONFIRMED

CANCELLED is reachable from every state above, including CONFIRMED. Accepting a service claims it and starts it, in one step.

  • Claiming sets the agent and the status together. An unclaimed, non-terminal service can be picked up by any agent whose role covers its type; doing so sets assigned_agent_id and moves it to IN_PROGRESS. Claiming a job and leaving it "Not Started" tells the agency nothing.
  • Status changes require an assignee. No agent on the row means status is not editable. An unclaimed "Confirmed" is a status nobody can stand behind.
  • Reassignment to another agent is owner-only. An agent may claim work; they may never hand it off.

Why type, not instance

"Chase the embassy on Monday" is Visa work whichever visa it is about. A trip holding three flights should not carry three separate follow-up lists that all read "nothing scheduled". Scoping to the type caps the lists at five per lead — four service types plus trip-level — regardless of how many instances exist. Scoping to the instance made the count grow with the services, and every one of them was empty.

Completed, not deleted. "We said we would call on the 20th and we did" is precisely the fact a customer disputes. Delete exists for a follow-up entered in error, and it writes a timeline entry when used. Every insert, complete or delete also recomputes lead.open_follow_ups and lead.follow_up_date in the same transaction.

05

Money, confirmations, paper trail

Quoted lines stay flat on the lead. Vouchers are new. Invoices extend what already exists.

Quoted lines stay flat

lead_proposal gains service_id and a service_label snapshot, and stays a flat list on the lead rather than nesting inside each service. A single invoice routinely covers flight and hotel together — that is how a trip is actually billed — and nesting would make it unrepresentable. A null service_id is a trip-level charge: agency fee, courier, anything spanning services.

The cancellation trap

A quoted line has no status of its own. Lines belonging to a CANCELLED service must be excluded from every total, so the filter runs through the owning service — otherwise a called-off service keeps quietly counting. This is why lead.quoted_*_total is recomputed on service status change, not only on proposal writes.

Invoices — extend, don't duplicate

The frontend has a lead-scoped invoice; the backend has an agency-wide client_invoice. This design adds lead_id, service_id, service_label and description to the existing table rather than creating a second one. A lead invoice is a client invoice that happens to name its lead; a null lead_id is a direct invoice raised outside any lead, which already exists today and must keep working. gst, total_with_gst and status stay server-derived on every write, and amount_paid stays cumulative — total paid to date, never a single receipt. This one needs your call — see Q1.

06

Derived vs stored

A column may only be stored if it names the list screen that needs it.

Computed on read — never stored

ThingDerived from
Trip Schedule (day by day)Every service's dated events, grouped by day. A flight yields one event per dated sector; a hotel yields check-in and check-out; a visa yields its appointment; a transfer yields one. Within a day the order is fixed — check-out, flight, transfer, appointment, check-in — the shape of a real travel day, deterministic without times. Never invent a time for a flight. Services with no dated events fall into a trailing "not scheduled yet" bucket.

Cancelled services are excluded from the lead's travel window and included in the Trip Schedule. The window is a commitment; the schedule is a record. Do not unify these.

07

Access control

Two independent axes. The frontend's version is a UX affordance — this one is the boundary.

Axis 1 — the lead belongs to the sales agent who took it. Lead-level fields (destination, status, travellers, dates, notes) are editable by the owning agent or the Agency Owner. Nobody else.

Axis 2 — a service belongs to whoever handles that type. An agent may edit a service when its type appears in their manageable_services, on any lead, whoever owns it. That is the whole point: a visa specialist works the visa on every lead in the agency.

The clause that is easy to drop and expensive to lose

An agent may also edit a service they are personally assigned to, even if its type is no longer in their manageable_services. Without it, an owner unticking "Visa" on an agent's profile instantly yanks that agent off work they are named on and half-way through — and that profile is editable in the agent form, so it happens.

The one unauthenticated surface

GET /api/public/proposals/{token} resolves a high-entropy token — never the lead's real id — reads the owning tenant schema through a REQUIRES_NEW cross-tenant transaction, and returns a hand-built DTO that is structurally incapable of carrying net cost, margin, agent ids, internal notes, timeline or invoices. Not a filtered entity: a separate class holding only what the customer may see. A controller-slice test asserts those keys are absent from the raw JSON, not merely null.

08

Query catalog

The proof for P1. One table, one WHERE, no join — per screen.

-- Leads list (owner). Value, follow-up badge and service count all inline.
SELECT id, client_name, destination, current_status, priority, assigned_agent_name,
       travel_date_from, travel_date_to, categories, quoted_selling_total,
       follow_up_date, open_follow_ups, service_count
FROM   lead
WHERE  is_active
ORDER  BY created_at DESC;

-- Cross-lead Services board: "every visa I handle, oldest first."
SELECT id, label, type, status, client_name, lead_destination, lead_id,
       assigned_agent_name, date_from, due_date, selling_total
FROM   lead_service
WHERE  type = ANY(:manageableTypes)
ORDER  BY COALESCE(due_date, date_from) NULLS LAST;

-- Unclaimed work anyone qualified can pick up.
…  WHERE type = ANY(:manageableTypes)
     AND assigned_agent_id IS NULL
     AND status NOT IN ('CONFIRMED','CANCELLED');

-- My follow-ups, overdue first.
SELECT id, lead_id, client_name, lead_destination, service_type, due_date, note
FROM   lead_follow_up
WHERE  assigned_agent_id = :agentId AND status = 'OPEN'
ORDER  BY due_date;

Lead detail is seven single-table reads by lead_id, issued in parallel — lead, lead_service, lead_members, lead_follow_up, lead_proposal, lead_voucher, lead_timeline — assembled into one response in the service layer. Seven index seeks beat one seven-way join, and each one is independently cacheable.

Note what is absent

Nothing in this catalog filters on tenant_id. Tenant isolation is the search_path set at connection-borrow time. Manual tenant filtering on a tenant-schema query is a bug, not a safety net.

09

Each row is one @Transactional method. Skipping any obligation is what makes a screen show a stale number — this table is the implementation checklist.

Cross-tenant caution

Any code that switches tenant mid-request must do the tenant-scoped work in a separate REQUIRES_NEW bean — self-invocation bypasses the proxy — and restore the previous tenant context in a finally block.

11

Open questions

Five calls needed before any code is written. Each carries a recommendation and its cost.

Q1

Invoices — one table or two?

Extend client_invoice with lead_id / service_id, or add a separate lead_invoice? A separate table leaves the finance module untouched but permanently splits the answer to "what does this client owe us", and every finance screen has to union them.

Recommend: extend. Cost — four nullable columns and one careful list query. Cost of the alternative — a reconciliation problem that never goes away.

Q2

The five visa booleans on lead_members

The existing traveller row carries passport_collected, photos_collected, forms_filled, submitted_to_embassy and visa_approved. This design moves them onto lead_service.visa_checklists.

Recommend: drop them in V2, since nothing is deployed. Keeping them means two places where the same tick can be written, and one of them will drift. If you prefer additive-only, we keep them documented as read-only-deprecated — the way the frontend already treats the legacy field.

Q3

Does the standalone visa table survive?

There is a visa table for cases raised outside a lead, with its own screen. Once a Visa service exists on a lead, the two overlap. Either keep both — that screen reads a union — or fold standalone cases into a lead-less lead_service row, which is a cleaner model but makes lead_id nullable and forces every query in §08 to think about it.

Lean: keep both. The screens serve genuinely different jobs, and the alternative weakens the strongest invariant in the design.

Q4

booking has no lead_id

The existing booking row is single-traveller and unlinked to any lead, so a multi-pax group lead cannot convert into one booking. Out of scope for this LLD — but it surfaces the moment a lead reaches BOOKED.

Flagging now so it is a decision rather than a surprise.

Q5

Hard delete on a service?

Cancelled work is expressed by status, not deletion (P7). Confirm that a genuine DELETE is still acceptable for a service added by mistake.

Recommend: allow it, and write a timeline row when it is used.
